# SGLang lane

Recipes in this directory are **draft inference recipes** for serving models with [SGLang](https://github.com/sgl-project/sglang) on **NVIDIA DGX Spark** (Grace Blackwell **GB10**, unified memory). Each populated recipe is a self-contained bundle: manifest, environment template, launcher, and author notes. Nothing here is verified until an author completes the checklist below, updates `recipe.json` status, and records `tested_at`.

## What belongs here

| In scope | Out of scope |
| --- | --- |
| HTTP/OpenAI-compatible **server** recipes launched via SGLang (`sglang.launch_server` / `sglang serve` per current SGLang docs) | llama.cpp or vLLM recipes (`recipes/llama-cpp/`, `recipes/vllm/`) |
| Single-GPU Spark deployments and multi-node Spark clusters when the author documents tensor-parallel / disaggregated setup | Training, fine-tuning, or RL rollout jobs unless the recipe is explicitly an inference endpoint |
| Model-specific tuning (context length, batching, quantization, attention backend) captured in `run.sh`, `env.example`, and README | Copy-paste launch commands without pinning package/container revision and recording Spark observations |
| Draft placeholders generated by `scripts/new_recipe.py` awaiting author invocation | Recipes that claim `verified` without benchmark evidence and output validation |


This lane has **no populated recipe**. Related public work on the same model,
not duplicated here: [r0b0tlab NVFP4 W4A16 on 2× GB10](https://huggingface.co/r0b0tlab/Qwen3.8-Flash-Next-NVFP4-W4A16-sm121)
and [companion SGLang repo](https://github.com/r0b0tlab/qwen38-flash-next-w4a16-sm121-sglang).
See [`docs/comparison-nvfp4-w4a16-sglang.md`](../../docs/comparison-nvfp4-w4a16-sglang.md)
before treating those NEXTN numbers as llama.cpp results.

SGLang recipes should cite **exact** SGLang and model revisions tested, document **launch mode and API surface**, and treat DGX Spark **unified memory** behavior as a first-class constraint (memory fraction, cache pressure, monitoring limitations).

## Create a new recipe

From the repository root:

```bash
python3 scripts/new_recipe.py \
  --runtime sglang \
  --slug baseline-server \
  --title "SGLang baseline server" \
  --summary "Draft baseline server recipe for a pinned model revision." \
  --model your-org/your-model \
  --revision your-tested-revision
```

Add `--root /path/to/repository` only when targeting a different checkout.

The generator creates `recipes/sglang/<slug>/` with `README.md`, `env.example`, executable `run.sh`, and `recipe.json` conforming to schema v1 per [`CONTRIBUTING.md`](../../CONTRIBUTING.md):

- `$schema`: `../../../schema/recipe.schema.json`
- `schema_version`: `1`
- `id`: `sglang/<slug>`
- `runtime`: `sglang`
- `hardware.target`: `NVIDIA DGX Spark`
- `hardware.gpu`: `GB10`
- `status`: `draft` with `tested_at`: `null`
- `entrypoint`: `run.sh`

**Draft `run.sh` fails closed** until you replace the placeholder with a pinned, tested invocation documented in the recipe README.

Slug rules: lowercase alphanumeric plus hyphens; one directory per recipe; do not duplicate an existing slug.

## Recipe author checklist (SGLang on DGX Spark)

Complete every section before setting `status` to `verified` and a non-null `tested_at` in `recipe.json`.

### 1. Package / container revision

- [ ] Pin the SGLang runtime immutably: exact PyPI version, git commit, or container image digest. Tags may identify drafts but are not sufficient for `verified`.
- [ ] If using Docker, document the image URL, digest, human-readable tag, and CUDA variant from [lmsysorg/sglang tags](https://hub.docker.com/r/lmsysorg/sglang/tags).
- [ ] Note any extra Python deps (flashinfer, modelopt, etc.) and how they were installed, per SGLang install docs for your platform.
- [ ] Store non-secret config in `env.example`; secrets (`HF_TOKEN`, etc.) only as variable names.

### 2. Model revision

- [ ] Set `model.repository` and `model.revision` to the exact repository and immutable revision loaded during verification (a commit SHA, not a mutable branch or tag). Mutable refs are acceptable only while `status` remains `draft`.
- [ ] Document gating, `trust-remote-code`, and custom chat template requirements if applicable.
- [ ] For quantized checkpoints (NVFP4, FP8, etc.), cite the checkpoint source and the SGLang quantization flags from current docs—do not assume a generic Qwen path works on Spark without verification.

### 3. Launch mode and API shape

- [ ] State server entrypoint (`python -m sglang.launch_server` vs `sglang serve`—match your pinned SGLang version).
- [ ] Document listen `host`/`port`, model path or `--model-path`, and exposed routes (OpenAI-compatible chat/completions, embeddings, etc.).
- [ ] Specify client contract: request JSON fields, streaming vs non-streaming, tool/function calling if tested.
- [ ] Document multi-node or tensor-parallel layout if used (world size, NCCL/IB env, worker hosts)—Spark QSFP/switch topologies belong in the recipe README.

### 4. Attention and backend choices

- [ ] Record `--attention-backend` (or equivalent) and why it was chosen for GB10/Blackwell, per SGLang and Spark platform docs.
- [ ] Note CUDA graph / compilation options if enabled and any warmup or capture failures observed.
- [ ] For MoE, hybrid SSM, or non-standard architectures, document prefix-cache / radix-cache applicability per SGLang model guides.

### 5. Context, concurrency, and batch settings

- [ ] Document effective context length (`--context-length`, `max_model_len`, or model default).
- [ ] Record concurrency targets: max running requests, batch sizes, chunked prefill, schedule policy—use names from your pinned SGLang CLI.
- [ ] Note disaggregated prefill/decode or speculative decoding only if actually tested.

### 6. Memory controls

- [ ] Record static memory fraction (`--mem-fraction-static` or successor flags) and KV cache sizing choices.
- [ ] On Spark **unified memory**, document starting fractions, OOM recovery steps, and whether buffer-cache flush was required (see Spark SGLang troubleshooting docs).
- [ ] Capture monitoring method: plain `nvidia-smi` vs other tools; note when GPU memory fields report `N/A` under UMA.

### 7. DGX Spark observations

- [ ] Hardware: DGX Spark, GB10, driver version, container runtime, single-node vs cluster.
- [ ] Cold start time, model load time, and warmup behavior (qualitative; no unsubstantiated throughput claims).
- [ ] Failures and workarounds tied to Spark (attention backend asserts, memory pressure, network for multi-node).
- [ ] Link to NVIDIA Spark SGLang instructions/troubleshooting for issues you reproduced.

### 8. Benchmark methodology

- [ ] Define workload: prompt distribution, output length, concurrency level, duration, and warmup policy.
- [ ] State client tool (SGLang bench scripts, `curl`, custom driver) and version.
- [ ] Report **reproducible** metrics only (tokens/s, TTFT, p50/p95 latency, success rate)—with hardware and batch settings that match the recipe.
- [ ] Separate cold-start from steady-state if both matter; store raw logs or artifact paths in the recipe README.

### 9. Output validation

- [ ] Functional checks: HTTP status, schema, streaming integrity, stop sequences, tool calls if applicable.
- [ ] Quality spot-checks: fixed prompts with expected properties (format, language, refusal behavior)—not production quality scores unless you define the rubric.
- [ ] Regression notes: what would fail if someone changes revision, backend, or memory fraction.

## Candidate recipe matrix (planning targets)

These rows are **lane planning targets**, not shipped recipes. Populate each with the interactive `make new` target or the `scripts/new_recipe.py` invocation above when you are ready to author and verify; do not treat this table as evidence that a recipe exists or that any configuration is validated on Spark.

| Target | Primary goal | Typical model posture | Author focus (configure from SGLang + Spark docs) | Verification emphasis |
| --- | --- | --- | --- | --- |
| **Baseline server** | End-to-end OpenAI-compatible serving on one Spark | Small or mid dense model (author-chosen revision) | Default attention backend for Blackwell, modest context, conservative memory fraction, single-GPU `tp=1` | Smoke test chat completion, health endpoint, stable load over short run |
| **Long-context** | Maximize usable context within UMA | Model variant that supports extended context at tested revision | Context-length flags, KV cache budget, batch vs memory tradeoffs, prefix/radix cache where applicable | Correctness on long prompts, OOM boundary documentation, latency at context extremes |
| **Constrained memory** | Serve larger or denser models under tight UMA | Quantized or smaller active-parameter model (author-validated checkpoint) | Lower static memory fraction, quantization flags from SGLang docs, reduced concurrency | Load success, steady requests without OOM, documented recovery steps |
| **Throughput** | Saturate GPU for batch/chat load | Model size matched to author’s concurrency goal | Batch scheduling, max running requests, chunked prefill, optional CUDA graphs | Steady-state tokens/s and latency percentiles with defined client load |

Suggested slug names when you create recipes (optional): `baseline-server`, `long-context`, `constrained-memory`, `throughput`—or model-specific slugs if multiple variants of the same target are needed.
