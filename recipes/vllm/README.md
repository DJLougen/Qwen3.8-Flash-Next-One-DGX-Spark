# vLLM lane

Recipes in this directory are **draft inference recipes** for serving models with [vLLM](https://github.com/vllm-project/vllm) on **NVIDIA DGX Spark** (Grace Blackwell **GB10**, unified memory). Each populated recipe is a self-contained bundle: manifest, environment template, launcher, and author notes. Nothing here is verified until an author completes the checklist below, updates `recipe.json` status, and records `tested_at`.

## What belongs here

| In scope | Out of scope |
| --- | --- |
| HTTP/OpenAI-compatible **server** recipes launched via vLLM (`vllm serve`, OpenAI-compatible server, or programmatic `LLM` / `AsyncLLMEngine` per current vLLM docs) | SGLang or llama.cpp recipes (`recipes/sglang/`, `recipes/llama-cpp/`) |
| Single-GPU Spark deployments and multi-node Spark clusters when the author documents tensor-parallel / Ray / distributed setup | Training, fine-tuning, or RL rollout jobs unless the recipe is explicitly an inference endpoint |
| Model-specific tuning (context length, batching, quantization/dtype, attention backend, compilation) captured in `run.sh`, `env.example`, and README | Copy-paste launch commands without pinning package/container revision and recording Spark observations |
| Draft placeholders generated by `scripts/new_recipe.py` awaiting author invocation | Recipes that claim `verified` without benchmark evidence and output validation |

vLLM recipes should cite **exact** vLLM and model revisions tested, document **serving API surface**, and treat DGX Spark **unified memory** behavior as a first-class constraint (GPU memory utilization, KV-cache sizing, monitoring limitations).

## Create a new recipe

From the repository root:

```bash
python3 scripts/new_recipe.py \
  --runtime vllm \
  --slug baseline-openai-server \
  --title "vLLM baseline OpenAI server" \
  --summary "Draft baseline server recipe for a pinned model revision." \
  --model your-org/your-model \
  --revision your-tested-revision
```

Add `--root /path/to/repository` only when targeting a different checkout.

The generator creates `recipes/vllm/<slug>/` with `README.md`, `env.example`, executable `run.sh`, and `recipe.json` conforming to schema v1 per [`CONTRIBUTING.md`](../../CONTRIBUTING.md):

- `$schema`: `../../../schema/recipe.schema.json`
- `id`: `vllm/<slug>`
- `runtime`: `vllm`
- `hardware`: NVIDIA DGX Spark / GB10
- `status`: `draft` with `tested_at`: `null`
- `entrypoint`: `run.sh`

**Draft `run.sh` fails closed** until you replace the placeholder with a pinned, tested invocation documented in the recipe README.

Slug rules: lowercase alphanumeric plus hyphens; one directory per recipe; do not duplicate an existing slug.

## Recipe author checklist (vLLM on DGX Spark)

Complete every section before setting `status` to `verified` and a non-null `tested_at` in `recipe.json`.

### 1. Package / container revision

- [ ] Pin the vLLM runtime immutably: exact PyPI version, git commit, or container image digest. Tags may identify drafts but are not sufficient for `verified`.
- [ ] If using Docker, document the image URL, digest, human-readable tag, and CUDA variant from [Docker deployment](https://docs.vllm.ai/en/stable/deployment/docker.html).
- [ ] Note companion pins that affect binaries: PyTorch, CUDA driver/runtime as observed on Spark, FlashAttention / flashinfer builds, and any custom extensions.
- [ ] Document `ipc` / shared-memory requirements when using containers with tensor-parallel or multi-process workers.
- [ ] Store non-secret config in `env.example`; secrets (`HF_TOKEN`, etc.) only as variable names.

### 2. Model revision

- [ ] Set `model.repository` and `model.revision` to the exact repository and immutable revision loaded during verification (a commit SHA, not a mutable branch or tag). Mutable refs are acceptable only while `status` remains `draft`.
- [ ] List tokenizer/processor revisions if they diverge from the weight snapshot.
- [ ] Document gating, `trust-remote-code`, custom architecture, and multimodal processor requirements if applicable.
- [ ] State weight storage format: BF16/FP16, AWQ/GPTQ/FP8/compressed-tensors, etc., with a link to [quantization](https://docs.vllm.ai/en/stable/features/quantization.html).
- [ ] Record `dtype` / `--quantization` (or equivalent engine args) **as run on Spark**; note KV-cache dtype overrides and accuracy spot-checks.
- [ ] If quantization is incompatible with a desired feature (speculative decoding, LoRA, tool calling), say so explicitly in the recipe README.

### 3. Serving API surface

- [ ] State server entrypoint (`vllm serve` vs programmatic engine—match your pinned vLLM version).
- [ ] Document listen `host`/`port`, model path or `--model`, and exposed routes (OpenAI-compatible chat/completions, embeddings, pooling, etc.).
- [ ] Specify client contract: request JSON fields, streaming vs non-streaming, tool/function calling if tested.
- [ ] Include minimal **recorded** request/response examples in the recipe README (not fabricated JSON).
- [ ] Document multi-node, tensor-parallel, or Ray layout if used (world size, worker hosts, NCCL/IB env)—Spark QSFP/switch topologies belong in the recipe README.

### 4. Compilation and backend observations

- [ ] Record attention backend selection (explicit flag or auto) per [attention backends](https://docs.vllm.ai/en/stable/design/attention_backends.html) and why it was chosen for GB10/Blackwell.
- [ ] Document `torch.compile` / CUDA graph / piecewise compilation choices and whether warmup or capture failures were observed.
- [ ] Record build flags or environment variables (`VLLM_*`, `CUDA_ARCH`, etc.) only if verified on GB10.
- [ ] Capture failures and fallbacks (unsupported op → eager mode) so the next author does not rediscover them.

### 5. Context, concurrency, and batch settings

- [ ] Document effective context length (`--max-model-len` or programmatic equivalent) and justify against GB10 memory.
- [ ] Record concurrency targets: `--max-num-seqs`, `--max-num-batched-tokens`, chunked prefill, schedule policy—use names from your pinned vLLM CLI.
- [ ] State expected workload shape: concurrent sessions, input/output token distribution, prefix-cache settings if used.
- [ ] Note speculative decoding only if actually tested.

### 6. Memory utilization and KV-cache controls

- [ ] Record `--gpu-memory-utilization` and whether Spark **unified memory** required a different ceiling than datacenter GPUs.
- [ ] If used, pin `--kv-cache-memory-bytes` and explain why it was preferred over utilization-based sizing.
- [ ] On Spark UMA, document starting fractions, OOM recovery steps, and display-reserved memory caveats from NVIDIA docs.
- [ ] Capture monitoring method: `nvidia-smi` vs other tools; note when GPU memory fields report `N/A` under UMA.

### 7. DGX Spark observations

- [ ] Hardware: DGX Spark, GB10, driver version, container runtime, single-node vs cluster.
- [ ] Cold start time, model load time, and warmup behavior (qualitative; no unsubstantiated throughput claims).
- [ ] Failures and workarounds tied to Spark (backend asserts, memory pressure, network for multi-node).
- [ ] Link to NVIDIA Spark vLLM playbook and troubleshooting for issues you reproduced.

### 8. Benchmark methodology

- [ ] Define workload: prompt distribution, output length, concurrency level, duration, and warmup policy.
- [ ] State client tool (`vllm bench serve`, custom asyncio client, `curl`, etc.) and version.
- [ ] Report **reproducible** metrics only (tokens/s, TTFT, p50/p95 latency, success rate)—with hardware and batch settings that match the recipe.
- [ ] Separate prefill-bound from decode-bound scenarios when both matter; store raw logs or artifact paths in the recipe README.

### 9. Output validation

- [ ] Functional checks: HTTP status, schema, streaming integrity, stop sequences, tool calls if applicable.
- [ ] Quality spot-checks: fixed prompts with expected properties (format, language, refusal behavior)—not production quality scores unless you define the rubric.
- [ ] Regression notes: what would fail if someone changes revision, backend, quantization, or memory fraction.
- [ ] Only after all checks pass: set `status: "verified"` and `tested_at: "YYYY-MM-DD"` in `recipe.json`.

## Candidate recipe matrix (planning targets)

These rows are **lane planning targets**, not shipped recipes. Populate each with the interactive `make new` target or the `scripts/new_recipe.py` invocation above when you are ready to author and verify; do not treat this table as evidence that a recipe exists or that any configuration is validated on Spark.

| Target | Primary goal | Typical model posture | Author focus (configure from vLLM + Spark docs) | Verification emphasis |
| --- | --- | --- | --- | --- |
| **Baseline server** | End-to-end OpenAI-compatible serving on one Spark | Small or mid dense model (author-chosen revision) | Default attention backend for Blackwell, modest context, conservative `--gpu-memory-utilization`, single-GPU `tp=1` | Smoke test chat completion, health endpoint, stable load over short run |
| **Long-context** | Maximize usable context within UMA | Model variant that supports extended context at tested revision | `--max-model-len`, KV-cache budget, batch vs memory tradeoffs, chunked prefill where applicable | Correctness on long prompts, OOM boundary documentation, latency at context extremes |
| **Constrained memory** | Serve larger or denser models under tight UMA | Quantized or smaller active-parameter model (author-validated checkpoint) | Lower utilization ceiling, quantization flags from vLLM docs, `--kv-cache-memory-bytes`, reduced `--max-num-seqs` | Load success, steady requests without OOM, documented recovery steps |
| **Throughput** | Saturate GPU for batch/chat load | Model size matched to author’s concurrency goal | `--max-num-batched-tokens`, concurrent client load, CUDA graphs/compilation, scheduler tuning | Steady-state tokens/s and latency percentiles with defined client load |

Suggested slug names when you create recipes (optional): `baseline-server`, `long-context`, `constrained-memory`, `throughput`—or model-specific slugs if multiple variants of the same target are needed.
